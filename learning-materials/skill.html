Skill（技能）

把"一次做成功的办法"打包成"以后照做就行"的可复用流程。

可复用 · 按需加载 · 渐进披露
01个人解释

我的理解是：Skill（技能）是给 Agent 的"操作手册"，把一套成熟的做法打包成它需要时能随时调用的能力。

这周我亲眼见证了一个 Skill 的诞生过程：让 Kai 往 GitHub 推代码，反复卡在"系统代理导致 TLS 握手挂死"和"凭证弹窗等用户点击"两个坑上。Kai 摸索出一套固定解法——绕开代理、禁用凭证弹窗、URL 内嵌令牌。它没有让这套解法只留在聊天记录里，而是把它写成了一个可复用的函数 safe_push，以后每次推送直接调用，不再重新踩坑。

这就是 Skill 的本质：把一次性的经验，沉淀成可复用的能力。一次成功靠运气，把成功路径固化下来，才能每次都稳定复现。

02核心机制与组成

Skill 长什么样

最简形态，一个 Skill 就是一个目录，里面有一个 SKILL.md 文件。这个文件顶部必须有 YAML 元数据，至少两样：

---
name: concept-learning
description: 把一个新概念生成结构化学习资料……
---

name 是技能标识（小写字母/数字/连字符），description 讲清"这技能做什么、什么时候该用"。元数据下面是给 Agent 的指令正文，也可以再捆绑脚本、参考资料等文件。

关键设计：渐进披露（Progressive Disclosure）

Skill 不是一股脑全塞进上下文，而是分三层按需加载——这正好呼应了上一份资料讲的"上下文要省着用"：

层级内容何时加载
第一层name + description启动时就注入系统提示，让 Agent 知道"有这么个技能"
第二层SKILL.md 正文Agent 判断任务匹配时，才读取全文
第三层附带脚本/资料正文里引用到、确实需要时才去读

这样 Agent 可以同时挂着很多技能，却只为当前任务消耗少量上下文。

03一个具体应用场景

场景：本次作业里那个"概念学习资料生成器"。

我要为"Agent、上下文、Skill"三个概念各写一份学习资料。如果我直接对 AI 说"帮我写 Agent 的学习资料"，得到的是一次性输出——换个概念（比如"注意力机制"）又要重新说一遍同样的要求，还得担心它忘了格式。

Skill 的解法是把"怎么生成一份概念学习资料"这件事本身写成一个技能：它规定了输入信息（概念名、背景、经历）、生成步骤（确认边界→查来源→写解释→拆机制→给场景→列混淆点→附来源→自检）、输出结构（五段式）、以及自检清单。有了它，无论下次是"注意力机制"还是"向量检索"，都是同一套流程，格式稳定、要求不会丢。

这正是 Skill 和"一次性提示词"的分水岭：Skill 面向一类可重复的任务，而不是某一个具体问题。

04易混淆问题与使用边界

最容易混淆的两点

  • Skill ≠ 一次性提示词。提示词针对单次问题；Skill 是泛化的流程，能处理一类任务。判断标准：把主题换一个，它还能不能用？能用才是 Skill。
  • Skill ≠ 独立程序。它本身不运行，是给 Agent 看的"操作说明 + 可选资源"，真正的执行仍由 Agent 完成。它更像"新员工入职手册"，而不是"一个能独立跑的服务"。

使用边界

  • 来源要可信。Skill 能给 Agent 注入指令、甚至让 Agent 执行代码，恶意 Skill 可能导致数据泄露。只用自己的或信任来源的 Skill，用前先审计。
  • 不是越全越好。Skill 写太长会挤占上下文，好的 Skill 用渐进披露把细节放到按需加载的文件里。
  • 要维护。Skill 里的做法会过时（比如某个命令失效了），要像维护代码一样更新它，否则会变成"过期的误导"。
