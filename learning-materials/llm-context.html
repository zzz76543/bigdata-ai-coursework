大模型的上下文（Context）

模型生成回复时能"看到"的所有文本——它没有真记忆，是上下文给了它记忆的错觉。

上下文窗口 · 工作记忆 · 记忆分层
01个人解释

我的理解是：上下文，就是大模型在回答你之前，脑子里一次性装进去的全部文字。模型本身是"失忆"的——你每问一句，它都是从零开始生成。它之所以看起来"记得"你们聊过什么，是因为每一次都把前面的对话历史、系统设定、工具结果，连同你这句话一起塞进去。

我这几天有个真实的困惑：我隔了一天才再找 Kai，它怎么还认得我的账号、还知道上次网络被阻断、还记得"PAT 要勾 repo 主项"这个坑？后来明白，不是它"记得"，而是这些关键信息被写进了记忆文件，每次开新会话时又被自动塞进它的上下文里。

所以我的结论是：上下文 = 大模型的"工作记忆"。它是临时的、有容量上限的、用完就清空的一块草稿区，和它"学过的知识"（训练数据）是两回事。

02核心机制与组成

上下文窗口（Context Window）

上下文窗口是模型一次能容纳的 token 上限。Token 大致可理解为"半个词"，窗口越大，一次能处理的对话、文档、代码就越多。比如当前主流模型能做到 20 万甚至 100 万 token 的窗口——大约相当于几百页文字。

一次请求里，什么会占上下文

成分说明
系统提示（System Prompt）告诉模型"你是谁、守什么规矩"，每次都在
对话历史之前每一轮的用户消息和模型回复，逐轮累积
工具结果模型调工具后拿到的返回值，也会回填进上下文
外部注入的记忆把长期记忆文件、检索到的资料塞进来
本次要生成的输出输出本身也占用窗口

一个反直觉的事实：上下文不是越长越好

随着 token 数增长，准确率和召回会下降，这被称为 context rot（上下文腐烂）——所以"往上下文里塞什么"和"还剩多少空间"同样重要。

这解释了为什么我让 Kai 干活时，它会主动读记忆文件、而不是把三天所有对话都摊开——精选有用信息，比堆得越多越好。

03一个具体应用场景

场景：连续三天、跨多次会话协作完成同一件事。

给课程搭 GitHub 仓库这件事，我前后找 Kai 好几天，中间换过好几次会话。每一次新会话开始，Kai 都不"记得"之前的事——是它的上下文被重新塞入了两样东西：一是系统设定（它叫什么、怎么和我沟通），二是记忆文件里沉淀的"网络会间歇性阻断""PAT 要勾 repo 主项""SSH 和 HTTPS 独立阻断"这些经验。

正因为这些关键信息被有选择地放进上下文，Kai 每次都能"接着上次"继续，而不是从零重新问我一遍账号、重新踩一遍坑。这就是上下文的威力：它把"长期经验"转化成"当场可用的短期记忆"。

04易混淆问题与使用边界

最容易混淆的两点

  • 上下文窗口 ≠ 训练数据。训练数据是模型"学过的知识"，是它出厂前看过的海量文本；上下文窗口是它"当下能参考的草稿"，是这次请求临时装的文字。前者是长期知识，后者是短期记忆。
  • 有上下文 ≠ 有真记忆。模型没有真正的"记住"，它只是每次把历史重新喂进去。历史一旦超出窗口被截断，之前的内容就真的"忘"了。

使用边界

  • 容量有限。窗口会满，满了之后早期内容会被压缩或丢弃，所以长对话要主动做"记忆沉淀"，把关键结论落到外部文件，而不是指望模型一直记得。
  • 塞太多会变差。context rot 意味着"信息越多越准"是错觉，要给上下文做减法、做精选。
  • 敏感信息会留在上下文里。上下文里的内容会参与处理，因此不要把 API Key、密码这些随手贴进对话。
