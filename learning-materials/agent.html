Agent（智能体）

一个会自己动手、自己决定下一步该做什么的 AI——不只是回答问题，而是真正把事情办成。

大模型 · 工具调用 · 自主决策
01个人解释

对我来说，Agent（智能体）不是"会聊天的机器人"，而是"能自己动手干活的 AI"。聊天机器人只会回答"怎么做"；Agent 会真的去把事做出来。

这一周我有切身体会：我让一个 AI（我叫它 Kai）帮我建 GitHub 课程仓库。它不是回我一句"你去网页上点这几个按钮"，而是自己去读文件、探测网络通不通、选推送通道、写脚本、把代码推上 GitHub。中间踩了好几个坑——令牌权限不够、凭证弹窗卡死——它自己诊断、换方案，最后把仓库推上去了。

所以我的理解是：Agent = 大模型 + 能调用工具 + 能自己决定下一步。模型负责"想"，工具负责"做"，而"自己决定下一步"才是它区别于普通对话的关键——它不是在一条写死的流程里走，而是根据每一步的结果动态调整。

02核心机制与组成

Agent 工作的本质是一个循环：感知 → 决策 → 行动 → 观察结果 → 再决策。它每走一步，都根据上一步的结果决定下一步，而不是一次性把路线定死。

四个关键组成

组成角色我看到的对应物
大模型（大脑）理解任务、拆解步骤、做决策Kai 判断"该走 HTTPS 还是 SSH"
工具（手）执行具体动作：读写文件、跑命令、调 APIKai 跑 git push、调 GitHub API
记忆（经验）记住上下文和过往经验，避免重复犯错Kai 把"PAT 要勾 repo 主项"记进 MEMORY.md
编排（流程）把上面几样串成一个可控循环先探测网络 → 再选通道 → 再推送

Anthropic 在《Building effective agents》里画了一条重要界线：工作流（workflow）是"代码写死的固定路径"，Agent是"模型自己决定路径"。很多场景用简单工作流就够，只有当任务需要模型临场决策时才值得升级成 Agent。

03一个具体应用场景

场景：给一门课程搭一个能持续维护的 GitHub 作业仓库。

这个任务表面是"建个仓库"，实际是一串需要临场判断的子任务：网络被阻断要走哪个通道？SSH 和 HTTPS 哪个此刻通？令牌权限对不对？推不上去是网络问题还是配置问题？这些问题没法预先写死，只能边走边判断。

Agent 在这里的价值就体现出来了：它先探测各通道状态，发现 HTTPS 通、SSH 断，就用 HTTPS 推；推的时候卡在凭证弹窗，它就诊断出是 credential-helper-selector 在等用户点击，于是改走 URL 内嵌令牌绕过；最后再把这套"绕代理 + 禁弹窗 + 内嵌令牌"的办法沉淀成一个可复用的函数。

整个过程中，人只需要做两件机器做不了的事：登录账号、点一次"确认"。其余判断和执行都交给了 Agent。

04易混淆问题与使用边界

最容易混淆的两点

  • Agent ≠ 聊天机器人。聊天机器人只生成文字；Agent 会调用工具、改文件、跑命令、产生副作用。判断标准可以借用一句话："如果大模型能改变程序的控制流，它才是 Agent；如果流程是代码写死的，它就不是。"
  • Agent ≠ 越复杂越好。Agent 用更长的耗时和更高的成本换更强的任务能力，不是所有任务都值得。能用一个函数搞定的事，别硬上 Agent。

使用边界（它做不到什么）

  • 不是无限自主。好的 Agent 有明确边界：不删不该删的文件、不碰个人隐私、做危险操作前要人确认。我这几天就观察到它在"删文件""改配置"这类事上会先征求同意。
  • 不能替你承担后果。Agent 做的外部动作（发邮件、推代码、公开内容）后果仍由人负责，所以关键动作需要人把关。
  • 会犯错，且可能自信地犯错。它给的结论要能验证，不能因为是 Agent 说的就全盘接受。
